Workflow

How changes landed today

Read this before pushing

COLLABORATING.md section 10 still says stop at git commit and do not push. On 2026-09-17 Kevin authorized landing changes through pull requests directly in chat. Get that go-ahead each session; do not assume it carries over.

Main is protected: a pull request is required, admins are included, the branch must be up to date, and three checks must pass: Unit tests + typecheck, Detect secrets (gitleaks), and Vercel.

cd ~/Developer/fan-engage && git checkout main && git pull
git checkout -b fix/short-description
# make the change, run npm test in frontend/, commit with a conventional message
git push -u origin fix/short-description
gh pr create --base main --head fix/short-description --title "..." --body "..."
sleep 30 && gh pr checks N --watch --fail-fast
gh pr view N --json mergeStateStatus,mergeable -q '.mergeStateStatus + " " + .mergeable'   # must print CLEAN MERGEABLE
gh pr merge N --squash --delete-branch
git checkout main && git pull

# Verify the Production deploy for the new main SHA
SHA=$(git rev-parse HEAD)
ID=$(gh api "repos/JonasGroupEntertainment/fan-engage/deployments?environment=Production&sha=$SHA" -q '.[0].id')
gh api "repos/JonasGroupEntertainment/fan-engage/deployments/$ID/statuses" -q '.[0].state'   # poll every 30s until success

Adding an env var in Vercel does not redeploy on its own. An empty commit through the same recipe is the rebuild.

Database changes

  1. Apply the SQL to the correct project through the Supabase MCP first, and confirm with a select.
  2. Record it as the next numbered file in root supabase/migrations/ with the header line "Already applied to production via MCP on YYYY-MM-DD; kept here for the repo record."
  3. Add the matching rollback in supabase/rollbacks/.
